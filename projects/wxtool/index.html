03 / 桌面工具 · 二次开发

微语 / WXtool

面向 Windows 的微信聊天分析工具，整理沟通统计和分析结果。

基于 WechatVibe 二次开发

项目背景痛点与解法操作演示图文体验实现原理技术栈设计取舍

01 / 项目背景

先看清聊天事实，再决定如何理解。

聊天记录按时间不断向后累积。想回顾一段交流时，既需要找到具体说过的话，也需要了解消息数量、交流时段和双方发言情况。微语把这些观察放到一个工作台，给回看聊天提供清楚的起点。

项目基于 WechatVibe 二次开发，保留上游的聊天读取与分析能力，增加会话概览和快捷入口。产品思路是先呈现可以核对的统计，再由使用者选择原文、画像或分析工具，避免一打开就只看到模型结论。

为谁而做

面向希望回看自己有权访问的微信会话、整理沟通节奏的 Windows 用户。

核心能力

  • 沟通统计与分析工作台
  • 历史消息的分析与进度展示
  • 面向 Windows 的桌面使用体验

02 / 痛点与解法

把使用中的阻碍，变成明确的功能。

01

记录很多，缺少概览

遇到的问题
只看连续的聊天气泡，很难快速了解这一段交流的规模和节奏。
项目的做法
汇总已加载消息的数量、类型、平均文本长度、发言占比和小时分布。
02

找到一句话，仍缺上下文

遇到的问题
搜到关键词后，孤立的句子可能不足以理解当时讨论的事情。
项目的做法
支持关键词或日期搜索，点击结果定位原对话，并继续查看前后消息。
03

统计与推测容易混在一起

遇到的问题
消息数量与情绪、意图等模型判断性质不同，需要分别理解。
项目的做法
工作台统计独立于模型运行；分析另有入口，展示进度和待分析状态。

04 / 实现原理

一次操作，背后如何流转。

先限定样本，再解释数字

统计只处理已加载消息。未知发送者单独计数，无效时间不进入时段图；群聊将其他成员合并显示，避免把局部样本包装成完整关系结论。

桌面交互与分析分工

Electron 承载界面，Python 处理本机数据和任务，Node 负责模型调用。界面通过本机 HTTP 读取状态，模型计算不直接塞进页面交互代码。

切换账号也切换上下文

SQLite 文件按账号区分，历史游标校验账号与会话；前端在账号变化时取消旧请求并重置当前视图，减少旧结果串入新会话的风险。

05 / 技术栈

每一层技术，都有具体职责。

桌面容器
  • Electron

提供 Windows 窗口与受限桌面接口，加载本机服务提供的页面。

沟通工作台
  • HTML
  • CSS
  • JavaScript

组织会话选择、统计卡片、历史搜索和消息展示。

本机服务
  • Python
  • HTTP

读取消息、校验账号范围，提供历史查询与分析任务接口。

分析执行
  • Node.js
  • TypeScript
  • ONNX Runtime

执行本地 Laya，或通过模型连接器调用所配置的 API。

本地持久化
  • SQLite

保存会话选择、分析结果与进度，并区分账号和分析来源。

06 / 设计取舍

为什么这样设计。

本地能力与 API 各有边界

事实统计和本地 Laya 可在本机处理；远程 API 分析与聊天助手会发送相关上下文给所配置的服务。因此不能把整个产品描述为全程离线，模型推测也不能替代对原文的判断。

展示操作，不替代真实验收

展厅图片和视频使用合成聊天，视频未连接模型。它们说明工作台、搜索和统计如何使用，不证明分析准确度或各版本微信的兼容性；二次开发背景持续保留。
